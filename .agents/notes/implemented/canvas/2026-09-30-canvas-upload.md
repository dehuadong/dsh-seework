# Agent Note：画布右键上传本机图片

## 问题

画布上的图片只有两个来源：素材库里生成过的图，以及画布自己烧录的标注/裁剪合成图。用户手上已有的图片没有任何办法放上板——它既不是一次生成，也不是这块板改出来的。

需求：**在画布中右键 → 「上传图片素材」**，且只收 **PNG / JPEG**。

## 决定

1. **入口在板面的右键菜单里，不在工具栏。** 这个动作的含义是「把图放到这儿」：右键点在哪里，就是用户此刻指着的地方；菜单是板面上的 HTML（舞台坐标），任何缩放下大小不变，与「图层」列表同一做法。按下板面任意处或 Esc 关掉它。
2. **菜单只属于板面的空白处，图片上的右键不弹它。** 在既有图片上右键是关于那张图的；在那里摆出「上传图片素材」会读成"上传是针对这张图的操作"。所以右键命中卡片时直接放行，浏览器自己的菜单照旧出现（对图片而言有「图片另存为」，是有用的）。这条是用户实测报出来的（第一版菜单挂在整个板面上，卡片上的右键会冒泡上来）。
3. **上传的图片走画布自有素材。** 与标注/裁剪同一条路：`POST canvas/asset` 落到 `<数据根>/canvas/assets/`，卡片写 `source: 'canvas'` 与新增的来源 `origin: 'upload'`（徽标「上传素材」）。**不进素材库**——素材库记的是「生成过什么」，用户带来的图不是一次生成。
4. **只收 PNG / JPEG，判定在读取之前。** 文件选择框的 `accept` 是给人看的；真正的判定是 [`src/client/canvas-upload.ts`](../../../../src/client/canvas-upload.ts) 的 `isUploadableImage()`：媒体类型白名单，只有浏览器没给类型时才退回扩展名。被挡下的文件**报出文件名并说明没上传**，而不是静默丢弃。
5. **宿主那条路由不动。** `canvas/asset` 继续接受 PNG/JPEG/WebP/GIF，因为标注与裁剪共用它、产物是 PNG；「上传只收两种格式」这条合同由上传这条路自己保证。
6. **`image/jpg` 归一成 `image/jpeg`。** 它不是注册媒体类型但系统确实会这么报，而宿主是从 data URL 里读类型的——原样发过去会被拒。
7. **尺寸不自己量。** 落盘响应已经带回图片宽高（宿主读容器头），浏览器不必再解码一次。
8. **多选时横向排开、整组居中**，复用 `centeredImageCard` 的尺寸数学。为此 `PlacedImage` 多了可选的 `source` 字段：**这是 e2e 抓到的真 bug**——不加的话卡片默认成素材库来源，图片指向 `library/image/…` 而 404。
9. **合法来源收成一份清单。** `protocol.ts` 导出 `CANVAS_CARD_ORIGINS` 与 `isCanvasCardOrigin()`，宿主 `normalizeCard` 用它判断，类型与校验不再各写一遍。
10. **移除提示按来源说实话**：上传图片是「这张上传图片的文件也会一起删掉」，合成图仍是「这张合成图的文件也会一起删掉」——把上传的图叫合成图是假话。

## 备选方案

- **工具栏加一个按钮**：入口离动作远（按钮在顶上，图要落在中间），而用户明确要的是右键。驳回。
- **上传进素材库**：素材库是生成记录；与标注/裁剪同一条纪律，本机图片不该混进去。驳回。
- **浏览器里自己解码量尺寸**：多一次解码，且宿主已经把宽高算好放在响应里。驳回。
- **只允许单选**：多选是文件选择框的天然能力，一次选几张就横排落在视野中央，没有额外交互成本。采纳多选。
- **`role="menu"` / `role="menuitem"`**：第一版这么写，e2e 立刻红了——显式 role 覆盖掉了 button 角色，而用户要的恰恰是一个「按钮」；而且这套 ARIA 菜单还承诺了并未实现的键盘语义。改为普通按钮 + `role="group"` 容器。
- **菜单在任何位置都弹（含图片上）**：第一版就是这样，用户报「在图片素材上右键也出现了上传图片素材」。驳回，见决定 2。
- **卡片右键给一套卡片自己的菜单（加入到对话框 / 标注 / 裁剪 / 移除）**：那是一个新的产品决定，且卡片已有的浮出指令条和 ✕ 已经覆盖这些动作。本次不做；卡片上的右键放行给浏览器菜单。

## 后果

- 画布多一个入口；上传的图片属于板子自己的素材：删卡片时文件一起删，工具栏「清理无用图片」也清得到它。
- 来源徽标多一种「上传素材」；旧板子不受影响（没有这个来源，推断逻辑照旧）。
- 格式把关只在 UI 一侧。宿主路由仍是通用的「写入一张画布图片」，这是刻意的：它服务三种产物，不该为其中一种收窄。
- `centeredImageCard` 现在会带上 `source`（当调用方给了）。素材库那条路不传，行为不变。
- 入口需要一块**没有被卡片盖住的板面**：板子铺满时得先挪开或平移视野。这是「菜单属于板面空白处」的代价，换来的是右键图片不会出现与那张图无关的动作。
- 图片上右键现在落到浏览器自己的菜单（可「图片另存为」）。卡片自己的右键动作（若有）留给以后的产品决定。

## 验证

- `npx playwright test` 整跑 **10 passed**（20.4s）：[`e2e/canvas-upload.spec.ts`](../../../../e2e/canvas-upload.spec.ts) 四条 + 原有六条。四条分别断言：板面空白处右键后菜单与「上传图片素材」出现；**在图片上右键不弹这个菜单**（同一条用例里先在空白处弹出作为对照，再右键刚上传的那张卡，断言菜单消失）；走**真实 filechooser** 上传一张 PNG 后板上**只多一张**卡片（用前后 id 差集判定，不依赖板子的初始内容）、徽标为「上传素材」、`img` 指向 `canvas/asset` 路由且 `naturalWidth > 0`；上传 GIF 被挡下——出现「只支持 PNG / JPEG」提示且卡片数不变。
- spec 里「空白处」是**扫描**出来的（`elementFromPoint` 找第一个不被卡片或菜单盖住的点），不是假设角落为空：临时 home 留着历次运行的板子，且每次上传都落在视野中央。
- `pnpm typecheck`：通过。
- `pnpm test`：37 个文件 514 通过、1 跳过。新增 `src/client/canvas-upload.test.ts` 5 条（两种格式接受、其它图片格式与 PDF 拒绝、只在浏览器没给类型时才看扩展名、`image/jpg` 归一）；`src/canvas-store.test.ts` 补一条「五种已知来源都保留、未知来源清空」。
- 红-绿记录：spec 先红（锚点与菜单都还不存在）；实现后第二次红在「上传的卡片指向素材库路由」——即 `centeredImageCard` 不带 `source`，是真缺陷；补上字段后转绿。用户报「图片上右键也弹菜单」后，先加「图片上右键不弹菜单」一条（红：菜单计数 1），再改代码转绿；同一次修正暴露了 spec 自身的缺陷——原来的「板面右键」点的是板面**中心**，而卡片正落在那里，于是正例也红了，改为扫描空白点后才稳定。
