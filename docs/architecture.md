# dsh-seework 架构

## 两半结构

DSH 插件由宿主半边和浏览器半边组成，同一个 npm 包两个入口：

| 半边 | 入口 | 运行位置 | 职责 |
| --- | --- | --- | --- |
| 宿主 | `lib/index.js`（`exports["."]`） | DSH 宿主进程（Node） | 设置区、`/api/dsh-seework/*` 路由、生成任务（每模型 1 并发、不排队）、素材库落盘、Agent 工具、系统提示词公告 |
| 浏览器 | `lib/client.js`（`exports["./client"]`） | dsh web GUI | 设置卡片（槽位或浮动面板）、素材库、画布、右上角入口、**会话内的图片卡片** |

宿主半边在 `cordis.patch.yml` 里以裸包名插入 profile 装配表；`package.json` 的 `dsh.client` 声明让浏览器半边从 `/plugins/dsh-seework/client.js` 加载。

## 宿主半边

```
src/index.ts            apply()：装配设置区、路由、Agent 工具、公告
src/settings.ts         设置文档：schemastery schema、生效值归一化、模型解析
src/capability.ts       能力表：模型形状（schema 片段 / 读回 / 合并 / 退役键 / 与目录新读法比对与采纳）+ 请求解析（默认值、裁剪、上限）（#669）
src/protocol.ts         两半共享的线协议（常量、请求/响应、素材记录）
src/engine.ts           请求映射 + 调 SeeAI Hub + 响应归一化
src/catalog.ts          模型目录发现（catalog 优先，/models 兜底）
src/catalog-refresh.ts  自动检测：启动 / 开卡片 / 低频后台三个触发共用一条路径与节流
src/generation-runtime.ts  生成任务（每模型 1 并发、忙即拒、取消、等待、落库）
src/library.ts          本地素材库（文件 + index.json）
src/routes.ts           /api/dsh-seework/* 路由族（含工具结果图片的附件回读路由）
src/agent-tools.ts      generate_image（同步调用，结果里没有任务号；带可选的 reference_images 即改图）
```

关键约定：

- **设置是唯一配置源**。`installSettingsSection` 把 `dsh-seework` 命名空间注册进 `ctx.settings`；有设置服务时以它为准，没有时回退到装配条目（同一个 schema 即默认值）。API Key 是 `role('secret')` 字段，所有线面读到的都是脱敏值。
- **路由注册写在设置注入里面**。`ctx.effect` 是立即执行的，所以「先在外层 effect 里注册路由、再等 settings 注入」会永远查到服务不存在，于是一条路由都注册不上、而且不报错（实现期真的踩到了，现在由 `src/index.test.ts` 钉住）。`settings` 也因此不进 `inject` 数组：声明它会让整个插件（含 Agent 工具）停在等服务上，而工具本来不需要设置服务就能注册。
- **两个地址，两个服务**。生成走 Gateway（`apiUrl`），模型目录走 service（`serviceUrl`）——`docs/api/README.md` 明确两者「路径互不代答」，所以目录地址必须是独立设置；发现逻辑会依次尝试 service 目录、网关同路径、OpenAI 兼容 `/models`，并把每一次尝试的结果回报给界面。
- **每模型 1 个并发，插件不排队（#658）**。SeeAI Hub 对「同一用户同一模型」只允许一个在飞的生图请求。插件**不排队**：同模型已有任务在跑时，第二次提交**直接拒绝**（告诉用户"本次没有发起生成、也没有扣费；得到许可后再发"），**不同模型互不影响**。**409 不重试**：去队列后本地不会再产生 409，收到即代表那把锁被**别的进程/实例**持有（或上一轮留下的锁），退避几秒再发不是"重试"而是再违反一次同一条规则。`generation-runtime.test.ts` 钉住「同模型第二次被拒」「不同模型并行」「409 只发一次」。
- **请求按能力表裁剪**。`capability.ts::resolveRequest`（#669 前叫 `normalizeRequestForModel`，随模块搬进能力表）用目录存下来的档位/比例/格式/参考图能力裁剪请求：表里没有的值一律不发（发了就是 400）。空列表的含义由 `capabilitiesKnown` 决定——目录描述的模型「没列 = 不接受」，裸 `/models` 只给了名字则原样透传，因为那时确实无从判断。（**#661**：画质不在裁剪之列——它已不是插件的参数，无论目录怎么声明都发不出去。**第十三批 / #663**：能力表改从 `supported_parameters` 描述符读，**整个键缺失 = 能力未知**，与裸 `/models` 同一纪律——不裁剪、不猜；见下面的「目录条目 v2」。）
- **密钥不出宿主**。浏览器只调本机同源路由；上游调用、密钥注入、响应下载都在宿主完成。
- **字段词汇严格对齐契约**。`buildGenerationBody` 只产出 `docs/api/images.md` 列出的字段——SeeAI Hub 对未知字段返回 400 `unknown_field`，多写一个字段就是硬失败。`resolution` + `aspect_ratio` 与显式 `size` 互斥，所以插件只用前者，永不猜像素尺寸。`watermark` / `seed` 是 doubao 协议的**请求参数**（缺省即网关/上游的默认：不加水印、种子随机），**能不能传以该模型目录声明的字段为准**——目录声明了就由 Agent 放进 `params` 传，插件既不设开关也不补值（**第八批更正**：第三批曾把它们当成"插件设置 owner、由 `engine.ts` 注入"，那是错的，见下面的「水印与种子回归普通参数（第八批）」。**第十一批 / #659 更正**：`params` 通道整条删除，声明了的字段也发不出去。**第十三批 / #663**：`watermark` 不在插件的五个常规参数内——插件**永远不发**它；"用户没选时显式发 `false`"是 seeaitv 侧的事，插件没有这个通道。）
- **设置卡片不让人填路径，也不只是只读**。素材目录用宿主自己开的选择窗口挑：真正的实现是 DSH 的接缝 `ctx.directoryPicker`（`dsh web` 的 `directory-picker-auto` 行按环境挂 `native` 或 `browse`），插件**按结构消费**它（`src/directory-picker.ts`，不引入 DSH 包依赖），且**不写进 `inject`、每次请求现探**——服务可能晚于插件挂载，缺了它插件必须照常工作（同 `conversation` 的规矩）。两条路由分工明确：`POST settings/directory-picker` 只报能力、**不开任何窗口**（卡片据此决定显不显示按钮；接缝文档的规矩是驱动不了的能力就把入口藏起来），`POST settings/pick-directory` 开一次窗口等结果；请求带 `AbortController` + `req.on('close')`，页面一走就 abort，免得宿主屏幕上留一个没人管的对话框。用户先要求「不应该手动填写地址」，只读之后又要求「打开资源管理器选择目标地址」，所以现在的形态是「选择目录… / 恢复默认」两个按钮 + 宿主报上来的真实路径。

关键约定：

- **不依赖非基线客户端包**。客户端包只把 `react` / `react-dom` / `@deepseek-ai/cordis` / `dsh-client-ui-slots` 作为外部模块，其余全部内联；设置卡片的表单控件因此自带，不引入 `dsh-client-ui-primitives`（它会拖进整套语法高亮依赖）。
- **浏览器半边绝不能碰宿主侧文件**。两个坑都踩过、也都加了自动检查：一是 tsdown 0.15 **没有** `deps.neverBundle` 选项，写了会被静默忽略，于是 React 被内联进 bundle——两个 React 实例一渲染就 hook 报错；二是客户端模块若（哪怕间接）导入宿主侧文件，`node:crypto` 之类的内建模块会被打进浏览器 bundle，而模块加载器解析不了它，整块客户端半边直接加载失败（表现是「按钮从来没出现过」且没有可见报错）。共享常量因此放在零依赖的 `canvas-limits.ts`，`scripts/probe-host-bundle.mjs` 在真实宿主上校验这两件事。
- **设置必须可达，而且只出现一处**。首选座位是设置对话框**左侧导航**的 `settings.section`（`id: dsh-seework`、`order: 40`，排在自带的 10/15/20 之后，导航项文案 `SeeWork`）；**只有**拿不到该槽位时，才退回**插件分区里的 tab** `settings.plugin.item`；两个都没有才退化为浮动按钮 + 面板。两者的先后不确定（槽位声明可能早于也可能晚于本插件装配），所以两条路都要收：导航页被接受时 dispose 已注册的 tab；tab 的延迟回调在注册前先问一句"导航页是否已经占了"。少任何一条，同一张卡片就会在两处同时出现（第一版就是这样，被用户当场指出）。外部插件不允许让 GUI 启动失败，也不允许自己不可配置。
- **连接字段分两步写**。地址与 Key 先在界面上暂存，「检测可用模型」用界面上的值探测，「保存连接」才落盘——密钥是写后不可读的，误覆盖无法挽回。
- **同屏只开一个 SeeWork 面**。设置面板、素材库抽屉、画布浮层都是挂在 `document.body` 上的兄弟节点，不共享 React 状态；其中一个打开时通过 `dsh-seework-activate` 事件让其它面收起。
- **三个启动按钮共用一个 dock**。`surfaces.ts` 拥有 dock 元素并做属性查找复用，各面把自己的按钮放进去——三个固定坐标的按钮会互相压住，而且每加一个面就得多调一次偏移。
- **入口优先挂进宿主标题栏，浮动 dock 只作兜底**。会话标题栏右上角对第三方开放 `conversation.session.header.utilities`（列表槽，可以并排放多个按钮），所以「素材库 / 画布」注册在那里；**标题栏只在会话里存在**，首页没有它，所以浮动按钮是**隐藏**而不是删除——`HeaderLaunchers` 组件自己上报挂载/卸载（`onHeaderPresence`），入口据此显隐。删掉它们会让首页变得完全进不去。
- **宿主没有推送通道，所以「刚生完图」靠轮询**。`GET /api/dsh-seework/library/head` 只回答「最新一条的 id 和时间、总共几条」，页面每 2 秒问一次（页面隐藏时跳过，失败时什么都不做）。第一次问只做「认领」，否则一进页面就会把整个素材库当成新东西；**空素材库答不出 id，所以第一条图必须算变化**，不能被认领掉。发现变化后**只做一件事：刷新共享素材库 store**（素材库 tab、画布的选图面板、启动按钮上的计数都读它）。
- **两个面是右侧栏的 tab 类型，不是浮层**。走 shell 的公共两段式注册：`ctx.sidebarRightTabs.register({ id, kind, title })` 声明类型，本体注册进键控槽 `sidebar.right.pane.tab`（key = 同一个 id），chip 标题进 `sidebar.right.pane.tab.title`；打开用 `ctx.sidebarRight.openTab(kind)`——**展开侧栏由控制器负责**，插件不碰布局。按钮的开关状态因此改成问 `sidebarRight.active()?.kind`，浮层兜底时才退回 `reportSurfaceOpen`。`dsh.client.inject` 里声明 `@deepseek-ai/dsh-client-ui-sidebar-right` 是为了让 boot 图把该客户端半边排进模块表；插件侧只在**类型**上引用它（`import type {}`），运行时一律通过 `ctx.get('sidebarRightTabs')` / `ctx.get('sidebarRight')` 取服务（守卫允许 `get`、禁止直接读属性），所以它不需要进 `CLIENT_EXTERNALS`，也不会被内联。
- **按钮的按下态来自各面自报，而不是事件**。用户可以从抽屉自己的「收起」关掉素材库，此时激活事件里仍然是素材库，所以面用 `reportSurfaceOpen` 把真实的开关状态登记给入口；入口问一句再决定是开还是收。
- **出图不进画布，只进素材库**。曾经做过「生完图自动开画布并把新图摆到中央」，按「素材库最新 id」判定「新」；用户明确要求取消（后台一次生图把屏幕重新排一遍太打扰），所以现在 `watchGenerations` **连画布 store 都不接收**——「出图不动画布」是结构上的保证，不是靠判断。要上板就自己从素材库选：画布里的「从素材库选图」把图落在当前视野中央（那条路径的数学仍与卡片构造共用 `canvas-placement.ts`）。
- **素材库 store 只有一份**。抽屉和画布的选图面板读同一个 `LibraryStore`；两份 store 就是两份缓存，其中一份必然过期。
- **素材库是视图，不是新数据**。第 2 阶段只读第 1 阶段已经在写的 `index.json` 与图片文件；筛选和按天分组都在浏览器里做（列表接口一次返回全部元数据），所以输入搜索是即时的、筛选不打网络。
- **读取失败不清空**。`LibraryStore` 刷新失败时保留上一次的条目并记录错误原因——侧边栏不能因为一次请求抖动就白屏。

## 会话里的图片卡片

生图结果的正文**故意是纯文本 JSON**（纯文本对话模型也要能用，改图需要的附件引用也靠它传回），所以工具调用那一行默认只是一墙 JSON。图片卡片是浏览器半边补上的那一层：`src/client/tool-card.tsx` 把 `generate_image` / `get_seework_task` 两个 wire 工具名注册进 shell 的键控槽 `tool.call.toolview`（命中 key 的视图**替换**通用行），卡片自己渲染标题、状态、消息和缩略图。`get_seework_task` **已经不对应任何工具**——SeeAI Hub 的图片接口是同步的，插件不再提供任务号，那两个任务工具随之删除——但它留在注册表里是刻意的：那个名字的历史结果已经写进会话日志，删掉键会让旧会话的卡片退化成裸 JSON（同画布仍读没有 `origin` 的旧卡片）。**`edit_image` 不享受这个待遇**（**第十四批 / #664**）：工具面合并成一个 `generate_image`（`reference_images` 成为它的可选参数）之后，那个键被直接删掉——开发阶段不保留历史渲染，旧会话里的改图行退回 shell 的通用行，图本身仍在素材库里。

三件事必须按这个顺序说清楚，否则很容易走错路：

| 决定 | 理由 |
| --- | --- |
| 图片引用取自结果的 `block.meta.images`，不是 `block.content` | 结果是纯文本，内容里没有图片块；`output.presentationMeta` 才是宿主随 `tool/result` 事件持久化的那份附件引用（重放也在）。客户端 block 同时带 `content` 与 `meta`，所以视图能读到它自己的元数据 |
| 字节自己取，走本机路由 `GET /api/dsh-seework/attachment/image?…` | shell 的两条现成路都不能用：① `tool.call.images` 画廊槽被内置 `read_image` 行声明为**子槽**，而子槽只允许一个声明者，第二个声明者会让整块客户端 bundle 加载失败；② shell 会话授权的 `loadImage` 只认「会话日志正文里引用过的附件」，工具结果的图**按设计不在正文里**，会被拒。于是宿主加了这条只答本机的路由：完整引用逐字段重新校验（附件 id、媒体类型白名单、三个正整数），再调 `ctx.attachments.readImage(ref)` 回字节 |
| 注册要带**独立的优先级** | 同一台机器上可能装着另一个生图插件，它也会为自己的工具名注册视图——撞名的那个键是 `generate_image`。键控槽对「同 key 同优先级」是**直接报错**，而且报错会连累**输的那一方整个插件加载失败**（真机实测：对方 loader entry 失败，界面弹「Failed to load plugins」）。所以这里注册在 `priority: -10`——既避开冲突，又因为「优先级数值最小者渲染」而由本卡片出图；本卡片读的是 `meta`，两个插件的 `meta` 字段名一致，因此对方的生图结果同样能正常显示 |

失败策略与其他面一致：读不出来就不渲染（`imagesOf` 对每条记录逐字段校验，半合法的一条直接丢掉），图片 404 时缩略图位置显示「图片已不可读」而不是留一个破图，视图本身绝不抛错。

**卡片的宿主是折叠区，所以图片还得进正文**。已完成轮次的过程内容在对话里默认是折叠的（shell 的「对话显示」设置：标准 / 紧凑），工具调用那一行就在里面——用户不展开，看到的只是一行「N 次工具调用」。而**助手自己的回复是正文里的 Markdown**，所以插件让模型把图放进回复：工具结果为每张图多给一个 `absolute_url`（`http://127.0.0.1:<GUI 端口>` + 素材库地址，端口取自 `ctx.webServer.port`，拿不到就不给、不编一个），**怎么用它由工具描述讲**（「在回复里写 `![简要说明](absolute_url)`」是工具级调用约定，见第五批）。两个硬约束让这件事只能这么做：

- shell 的 Markdown 渲染器只认**绝对** http(s) 图片地址（或它自己的路径表），相对地址会退化成 alt 文本——这就是必须算绝对地址的原因；
- 用户消息那一侧不渲染 Markdown（实测：把 Markdown 图片写进用户消息，界面上只是原文），能承载图片的正文只有助手回复。

这条路上图片不进模型上下文（只多了一段 URL 文本），纯文本模型照样可用。

## 画布上的浮动指令条（第一批）

在画布上点中一张图片，插件在它旁边浮出一条指令条（`src/client/NodeFloatingBar.tsx`）——用户此刻想作用于**这张图**，动作就该在它旁边，而不是在远处的工具栏里。

| 面 | 实现要点 |
| --- | --- |
| 位置 | 纯函数 `src/client/floating-bar.ts`（照 seeaitv 的同名工具）：默认吸附节点**上方**，上方放不下就**翻到下方**，水平方向**钳在可视舞台内**（留 8px 边距）；坐标由 `boardToScreen` 换算，所以平移/缩放都跟着走。条宽**渲染后实测**（中文标签宽度不可预知），没量到之前先 `visibility: hidden`，免得闪在角落 |
| 归属 | 条是**舞台坐标**里的 HTML（不在 `world` 那层），所以任何缩放级别下大小不变、也不跟着世界变换 |
| 反馈 | 输入框可能在屏幕另一头，所以失败时按钮自己改文案（「放不进输入框」，2.5 秒后复原），成功则什么都不说——草稿附件出现在输入框里就是反馈 |

**「加入到对话框」**（`src/client/composer-draft.ts`）把图片塞回当前会话的输入框当草稿附件，用的是 shell 自己的草稿机制，**不需要宿主路由、也不写素材库**：`fetch` 图片 → `File` → `conversation.createDrafts(sessionId, [file])` → 会话输入框的 `inputActions.addAttachments(ids)`；输入框忙（拒绝 id）时把草稿 `releaseDraftAttachments` 还回去，不留悬挂的 object URL。

两处来源必须分开看，否则很容易写成"时好时坏"：

- **会话身份来自槽位**：`sessionId` 与 `inputActions` 是 shell 发给**会话作用域槽位**的标准 props，所以我们的素材库 / 画布 tab 本体挂载期间才发布这份 face（`setComposerFace`）；没挂 tab 就没有会话上下文，按钮**隐藏**而不是假装能用——首页的浮动面板属于这一种。
- **服务要在用的那一刻探**：`conversation` 服务是 `ctx.get('conversation')` 探出来的，而且**不能在 apply 时探一次就存下来**。第一版就是这么写的，真机上一直失败：插件按 boot 顺序装配，我们 apply 时对话插件还没注册，于是存下的是 `undefined`。现在存的是**探针**（`setComposerProbe(() => probeService(ctx, 'conversation'))`），每次用时解析一次。

## 标注与裁剪（第二批）

标注与裁剪都产出**画布自己的图片**：`<数据根>/canvas/assets/`，走 `canvas/asset` 路由（`POST` 写入、`GET <asset>/<file>` 读回），画布卡用 `source: 'canvas'` 标明来源（缺省即素材库，所以老画布文档照旧能读）。**它们绝不进素材库**——素材库记的是"生成过什么"，而涂改过的一张不是一次生成；真机核对时确认过素材库条目数前后不变。

**来源与生命周期**（用户反馈：「移除的提示还是显示不从素材库删除……也不方便用户清理；画布中的素材产物能不能区分对话生成的、画布合成的、面板生成」）：

| 面 | 实现要点 |
| --- | --- |
| 来源标记 | `CanvasCard.origin`：`chat`（对话生成）/ `panel`（面板生成）/ `annotation`（标注合成）/ `crop`（裁剪合成），由 `canvasOriginLabel()` 转成徽标显示在卡片标题栏。前两者从素材库条目的 `source` 抄下来（`placeImage`、`canvas-add` 的 `complete()`），后两者在建合成卡时写入。**老卡片没有这个字段**：宿主 `normalizeCard` 只接受合法值（其余置空），客户端 `originOf()` 按 `source: 'canvas'` + `model`（旧版写「标注」「裁剪」）或按文件名回查素材库条目来推断，所以历史板子照样有徽标 |
| 删除语义 | `removeHint()` 按卡片类型给提示：合成图＝「这张合成图的文件也会一起删掉」，素材库图片＝「不会删除素材库里的文件」，备注＝「从画布移除」。**旧版对所有卡片都写死"不会删除素材库里的文件"**，对合成图是假话（它压根不在素材库里），而且删卡后文件永远留着 |
| 删卡连带删文件 | 顺序是**先改板、再删文件**：`store.removeCard` → `saveNow()` → `POST canvas/asset/remove`。宿主只在这一步算「还有没有板引用它」（`referencedCanvasFiles()` 扫全部板文件），被引用就 409 `asset_in_use`——所以删卡片和删文件不可能把另一块板上的同一张图抽走，反过来也不会误删 |
| 清理入口 | `POST canvas/assets` 列清单（每张图的 `bytes` 与 `referenced`，加 `orphans`/`orphanBytes` 汇总），工具栏「清理无用图片」调 `POST canvas/assets/prune` 删掉所有没人引用的（真机上用户的板子攒了 3 张孤儿、4.46 MB）。三条新路由都是 loopback + POST，且 `asset/remove` **注册在 `asset` 前缀路由之前**：前缀匹配是 `startsWith('<path>/')`，注册在后就会被当成文件名读走（`index.test.ts` 钉住了这个顺序） |
| 回报条自动收起 | 清理动作的结果用一条短提示回报（`showAssetNotice`，`NOTICE_MS = 4000`），4 秒后自己收起，新提示替换旧的（不会叠两条）。它报的是"刚做完什么"，**不是要一直读的状态**——用户实测报过「一直存在提示条，不消失」，所以它该有寿命，而不是等用户手动关 |
| 为什么仍留在数据根 | 合成图是**唯一副本**（只存了烧录后的 PNG，没存标注对象/裁剪框），放进缓存目录被清掉就是不可恢复的裂图。所以它留在 `<数据根>/canvas/assets/`：「清理」交给上面这个明确的入口，而不是交给缓存淘汰 |


| 面 | 实现要点 |
| --- | --- |
| 标注编辑器 | `src/client/AnnotationEditor.tsx` 弹窗铺满画布栏，里面是**一个居中的有界面板**（`width: min(100%, 1000px)`，压暗层 + 圆角投影面板）：顶部工具条＝**画笔 / 矩形 / 箭头 / 文字 / 橡皮擦** + 3 色 + 3 档粗细 + 撤销/重做 + 取消 + 保存。**多种标注同会话混用**（这是参考端 ADR-0016 的决策），保存时统一烧录成**一张合成图**。橡皮擦是**按对象擦除**（对象列表里没有像素可擦，拖过哪个删哪个，整步可撤销）；箭头由共享的 `arrowHeadPoints()` 同时喂给编辑器 SVG 与烧录，所见即所得。两条来自用户实测反馈的界面规矩：**头部一律实色**（工具条原本全透明，压在 88% 不透明的浮层上，背后的画布工具条从按钮底下透出来、字看不清）；**面板封顶 1000px 且居中**（画布栏可以拉成全屏，编辑器跟着铺满整屏就"太大"了——全屏时面板仍是 1002px、工具条回到一行） |
| 文字框：松手才出现 | `onPointerDown` 只记落点，`onPointerUp` 才开输入框。理由是浏览器的真实点击顺序 `pointerdown → mousedown → pointerup`：`mousedown` 会让浏览器挪焦点，按下就建的框会在**同一次点击里**建好又失焦，`autoFocus` 等于没有，用户一个字也打不进去（用户实测报的「文字标注功能不能使用了」就是这么来的——上一版给输入框加了「失焦即提交」，本意是"点别处也能确认"，结果每次点击都把框提交没了）。**不许再加 `onBlur` 提交**；失焦（Tab / 切窗口）不算结束 |
| 文字框：点框外即确认 | 确认放在浮层的 `onPointerDownCapture`（捕获阶段先于 SVG 的冒泡处理器），并且置一个「这次按下已经用掉了」的 ref 给冒泡阶段看：React 在两个监听器之间会重渲染，冒泡那个处理器看到的是"没有框"的新世界，不靠这个 ref 就会"确认一个标签的同时又开出下一个框"（真机上抓到的）。空内容只关框、不落标注 |
| 文字框自己管键盘 | 文字输入框开着时**文档级 Escape 必须让位**：否则按 Esc 想取消输入却把整个编辑器关掉（用户实测这么报的：「不想输入文字时只能回车」）。现在文档级处理里 `if (text !== undefined)` 那一支只做"取消这次输入"（顺带覆盖输入框没焦点时的情况：Tab 走开或窗口切回来，输入框自己收不到这个键），输入框自己的 Esc 只 `stopPropagation` + 清空输入，编辑器留着 |
| 切换工具后要等一拍 | 工具是 React state，点完按钮**同一个任务里**就派发指针事件时，处理器看到的还是旧工具（真机核对时第一版脚本就这么"画了个寂寞"）。真人点击天然隔着一帧，所以这只是核对脚本的坑；`AnnotationEditor.test.tsx` 用 `act()` 包住点击，避免同类假阳性 |
| 坐标体系 | 标注对象与裁剪框都存**原图像素**（`annotations.ts` / `crop-rect.ts` 是纯函数，可单测）；编辑器用 `viewBox` 把原图坐标直接当 SVG 坐标系，显示缩放交给浏览器；线宽按"自然像素/显示像素"换算，否则同一档粗细在 4K 图上是发丝、在缩略图上是色块 |
| 烧录 | `src/client/burn-image.ts`：离屏 canvas 按原图尺寸 `drawImage`，再依次画矩形（内缩半线宽）、笔画（round 线帽，单点画圆点）、文字（`textBaseline: top`，与编辑器左上定位对齐），最后 `toDataURL('image/png')`。这是全功能里唯一无法在 jsdom 里单测的部分（没有 2D 上下文），所以它保持极薄、只做 1:1 重放，全部坐标换算都在纯函数里 |
| 裁剪 | `NodeCropOverlay.tsx`：**节点原地**裁剪（不弹窗，裁剪是本地构图操作），三分格线 + 8 手柄 + 整体拖动，旁边浮一条工具栏（比例下拉 自定义/1:1/4:3/3:4/16:9/9:16 + 当前尺寸 + 取消/裁剪）。确认 → **新节点**（非破坏，原图保留）；覆盖层画在**屏幕坐标**里，所以缩放时框和手柄大小不变 |
| 撤销/重做 | 对象级：每次提交把上一份对象数组压进 `past`，重做用 `future`；Ctrl+Z / Ctrl+Shift+Z 同效（照参考端 ADR-0016 的对象级撤销） |
| 手势的坑 | 指针按下/移动/抬起可能落在**同一个任务**里（快速拖动或脚本化事件），所以"正在画的对象"同时存在 ref 与 state：`onPointerUp` 读 ref。只读 state 闭包时真机表现为"画完就没了"（第一版就是这样，真机核出来的） |

## 把对话里的图放到画布：手动一条路

「自动上板」被取消之后，用户要的仍然是「刚看到的这张图，能顺手放到板上」。于是做的是**手动版**（`src/client/canvas-add.ts` + 两处按钮），触发权完全在用户手里：

| 面 | 行为 |
| --- | --- |
| 入口 | ① 正文里点开大图后，灯箱底部有「加到画布」；② 工具调用那张卡片里，每张缩略图下面一个「加到画布」；③ **素材库**里也有两处：列表每张卡片元信息行末尾一个小按钮（放它展示的那张图）、详情浮层里标题行下面一个主按钮（放**当前翻到的那张**） |
| 点击之后 | 确保有板（没开就 `refreshList` → 打开最近一块，一块都没有就新建）→ **把画布调出来**（右侧栏 tab，拿不到右侧栏就退到浮动全屏）→ 有界等舞台报出尺寸（30 × 50 ms）→ 卡片落在**当前视野中央**（量不到就用 `ASSUMED_STAGE` 兜底，绝不放角落）→ 立即 `saveNow()` 落盘 |
| 为什么先关灯箱 | 灯箱是全屏遮罩，不先关掉就看不见右侧栏里刚放上去的图 |
| 为什么不弹提示 | 画布自己打开了，结果就在眼前，再加一条 toast 是噪音（用户原话：不需要提示，因为能看到结果） |
| 为什么卡片算「老图没有按钮」 | 板上的卡片引用**素材库文件名**，而旧版本的工具结果里没有这个名字（`presentationMeta` 后来才带上 `file`，更早的结果 JSON 里也没有）。历史卡片因此没有按钮；灯箱那条路对任何指向素材库路由的图都有效，老图照样能加。**素材库那两处天然没有这个问题**——它读的就是素材库记录本身，所以历史图片也都能加 |

素材库详情浮层里「复制提示词」的样子也在这轮改过：它以前是提示词段落下面一个不起眼的控件，用户反馈「和提示词文字混同，不知道这是按钮可以复制」。现在它与小节标题同行、右对齐，是带边框和底色的按钮（`variant="outline"` + `padding: 4px 12px`），提示词本身放进带边框、限高可滚动的 `<pre>`；实测计算样式为 `1px solid` 边框、有底色、`insidePromptBox: false`。

这一版重新引入了两样在取消自动上板时删掉的东西——画布的舞台尺寸发布（`publishStageSize` / `stageSizeFor`）与 `usableStage` / `ASSUMED_STAGE`。差别不在实现而在**触发者**：以前是后台生成自己动手，现在是用户点了才动，所以那份「量出可见舞台、量不到就兜底」的能力是必要的，而不是打扰。

**显示尺寸与放大由插件自己管**（`src/client/chat-images.tsx`）。生成图动辄 1–4K、几 MB，按原始尺寸渲染一张就占满整窗；而 Markdown 带不了尺寸，shell 渲染的那个 `<img>` 也不是我们的元素、给不了 class。所以：

- **尺寸上限用一条按 URL 前缀匹配的样式规则**：`[data-chat-anchor-key] img[src*="/api/dsh-seework/"]`（排除卡片自己的缩略图，它有 `data-dsh-seework-card-image` 并自带尺寸）——只可能命中本插件路由的图，素材库与画布的面板不在对话节点里，因此不受影响。
- **点击放大用捕获阶段的 click 监听**（`installChatImageZoom`）：命中上述图片且是「普通左键」时 `preventDefault` + `stopPropagation`，打开插件自己的灯箱（`Esc` 或点背景关闭）；`Ctrl`/中键照旧交给浏览器开新标签页。shell 的 Markdown 只渲染裸 `<img>`（没有链接），卡片里的链接则会跳成裸标签页——统一到灯箱比两套行为一致。
- 实测（临时实例 + 无头 Chrome，用历史会话里已有的回复图，零额度零模型调用）：原图 1536×864 → 正文里渲染成 320×180（`computedMaxWidth: 320px`、`cursor: zoom-in`），点击后灯箱以 1163×654 显示原图，点背景关闭。

## 素材库

```
<数据根>/                      默认 ~/.dsh/dsh-seework（设置里可改）
├── index.json                 条目数组（提示词/模型/参数/费用/来源/图片文件名+尺寸）
└── images/<uuid>-<n>.<ext>    真实图片文件
```

- 图片来源随结果一起下载或解码，尺寸从容器头直接读（PNG/JPEG/WebP/GIF），不依赖图像库。
- 条目上限 2000，超出按最旧淘汰并删文件。
- 图片路由只接受本 store 写出的文件名形状（`<uuid>-<n>.<ext>`），因此不存在目录穿越。
- index.json 损坏或条目畸形只影响该条目，列表接口不会因此失败。

## 阶段 2 / 3 的接缝

- **素材库界面**（第 2 阶段，已交付）复用 `library/list`、`library/remove`、`library/clear` 与 `library/image` 四个路由，以及 `LibraryEntry`。它没有给生成链路增加任何东西：生成时就写好的条目，换个视图看而已。
- **画布**（第 3 阶段，已交付）以同样的素材条目为素材来源：板上的一张图片卡只记 `file`（素材库文件名）+ 模型/提示词的快照，图片本身仍由 `library/image` 提供。画布文档与素材库共用数据根，但各占一个目录。

## 画布：为什么是空间板而不是节点图

用户明确要求不采用 dsh-imagegen 的节点方案，以 SeeAI TV 的画布为主。SeeAI TV 的板是**自由空间画布**（卡片带 x/y/宽高，视口是平移+缩放，整块板序列化），所以这里的模型同样是「摆在那儿的矩形」，没有端口、没有连线、没有数据流：

| 决定 | 理由 |
| --- | --- |
| 一块板 = 一份 JSON 文档 | 空间模型天然是一份文档；写入是「临时文件 + rename」，不需要数据库或增量日志 |
| 保存带修订栅栏 | 一份文档意味着后写者会覆盖前写者；栅栏让第二个窗口知道「别处改过了」，而不是静默丢失 |
| 冲突时保留用户版本并重试 | 板上是用户亲手摆的布局，用远端版本替换它是数据丢失；重试让「最后保存的人赢」变得可预期 |
| 保存回包**只带回修订号**，不替换本地文档 | 回包内容是「当初发出去的那份文档」的快照。如果照单全收，那么"请求在飞、用户又动了一下"期间产生的编辑就会被静默丢掉，而且 `dirty` 会被置回 false，于是这次编辑永远不会再被保存——实测症状就是**点「适应内容」没反应**（或点了之后又跳回 100%）。本地文档才是工作副本，所以只取 `revision`，并用编辑序号 `editSeq` 判断"飞在路上的请求之后是否又改过"，改过就保持 dirty 并再存一次 |
| 「适应内容」量不到舞台时**什么都不做** | 退化输入下 `fitViewport` 返回单位视口（100%、原点），照用就会把用户滚到哪儿都忘掉，看起来就是"素材全不见了"（用户就是这么报的）。所以：舞台尺寸**现场量**（不信任可能过期的缓存值），量到 0 或板上没卡片时直接返回；隐藏的兄弟画布实例**不允许把 0×0 发布出去**，否则会盖掉可见实例刚报的真实尺寸 |
| 出图不再自动上板 | 曾经按「素材库最新 id」判定「新图」并自动开画布、摆到中央，顺序还得是「先调出画布再刷新」（stage 只能由在屏幕上的板量出来，反过来卡片就落在视口左上角）。用户要求取消这套行为：后台生成一次就把屏幕重排属于打扰。现在 `watchGenerations` 只刷新素材库，签名里没有画布 store；`usableStage` / `ASSUMED_STAGE` 那套兜底也随之删除——上板只剩用户自己从素材库选图这一条路，那条路径量不到舞台时本来就不放卡片 |
| 卡片只存素材文件名 | 图片仍由素材库路由提供，画布不复制文件、不碰生成链路；删卡片不等于删素材 |
| 点中卡片就升到最上层 | 新卡 `z = max + 1`（`addCards`），渲染按 `z` 排序并写 `zIndex`。选中时（`selectCard`）若它不在最上面就 `updateCard(id, { z: top + 1 })`：刚放上来的图永远压在上面，不这么做的话，点一张旧卡想挪它，它会在拖动途中被后放的图盖住（用户实测反馈）。已经在上面的卡不重复改写文档（点来点去不该一直落盘）。被完全盖住的卡一个像素都点不到，只能靠「图层」列表（见下）找回 |
| 「图层」列表 | 工具栏开关（`[data-dsh-seework-layers-toggle]`）＋板面上一条紧凑列表（`[data-dsh-seework-layers]`）：**最上层排第一行**，行＝序号 + 来源徽标 + 提示词/备注。点一行＝`selectCard`（选中＋置顶），若那张卡不在视野里再把它挪到视野中央（`pickFromLayers`）。它是「被完全盖住的卡点不到」的唯一出路，也是唯一能一眼看全堆叠次序的地方 |
| 视口数学独立成纯函数 | 指针处理全部由 `canvas-viewport` 推导，任何缩放级别下拖动都不会漂 |
| 平移按「两次事件的步长」累加，不按「到起始点的总距离」 | 前者是幂等的：多一个监听器、重复投递一次事件，只会把同一段位移重复作用在已经前进的视口上；后者会让画布以「1+2+3…」的方式加速逃出视野。用户报「按住左键拖动，画布快速漂移」时，Chromium 实测正是这个二次累积（`CanvasBoard.test.tsx` 里两个板共用一个 store 的用例钉住它） |
| 引用了非法文件名则整单拒绝 | 那是客户端 bug，静默丢卡片会让人以为「图自己不见了」；其余畸形卡片（缺 id、未知类型、重复 id）丢弃即可 |

## 素材库记录都记了什么

`LibraryEntry` 是侧边栏与画布共同消费的形状，字段来源如下：

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `id` / `createdAt` | 生成时（`randomUUID` + 完成时间） | 排序、按天分组、删除定位 |
| `mode` / `model` / `prompt` / `resolution` / `aspectRatio` / `outputFormat` / `n` | 请求本身 | 详情展示、复现 |
| `quality` | **历史字段**：老条目里记着当时的画质；#661 起不再写值（新条目恒为空串） | 只为老记录仍能读回，界面不再展示（详情那一行改显示图片宽高） |
| `images[].file` / `mime` | 落盘文件名与嗅探出的类型 | 图片路由寻址、文件列表 |
| `images[].width` / `height` | 容器头解析（PNG/JPEG/WebP/GIF） | 详情展示，不需要图像库 |
| `cost` | 网关响应里的 `cost` | 侧边栏与详情的扣费显示 |
| `refNames` | 图生图的参考图名 | 详情里说明这张图基于什么改的 |
| `source` / `sessionId` | 调用方（Agent 工具 / 面板 / 画布） | 来源筛选与「哪次对话生成的」排查 |

## Agent 工具的结果里有什么

生图工具的结果是模型**唯一**能知道「图在哪」的地方：它拿到的是文字和元数据，看不到像素，正文里也没有图片（宿主只把图片渲染在工具调用旁边）。所以 `images[]` 里除附件引用外还带三个落点字段：

| 字段 | 内容 | 为什么要给 |
| --- | --- | --- |
| `file` | 素材库文件名（`<条目 id>-<n>.<ext>`） | 与素材库、画布卡片里记的 `file` 同一个标识 |
| `url` | 同源地址 `/api/dsh-seework/library/image/<file>` | 能直接引用/打开的地址（本机宿主提供） |
| `path` | 该文件在磁盘上的绝对路径 | 用户问「图存哪了」时唯一的准确答案 |
| `library_entry_id` | 条目 id | 在素材库里定位这次生成 |

- 三个字段由 `libraryImageLocation()` 统一算，**与落盘写入共用同一条命名规则**（不是各写一遍），因此报出来的位置不可能和磁盘上的文件不一致；`library.test.ts` 用「真的写一次、再比对」钉住这一点。
- 三个字段在**出入两个方向**都出现在 schema 里：工具结果带出来，模型把整个 image 对象原样传回 `generate_image.reference_images` 时也要照样通过校验（`restoreRef` 只读附件字段，其余忽略）。否则「原样传回」这句提示词就是假的。

## 能力技能与参数透传（第三批）

> **已被取代（第十一批 / #659）**：本节的**额外参数透传**整条通道（`capabilities.parameters` → `params` → 请求体）自本批作废——插件只发常规参数（**第十二批 / #661 起为五个**），`params`、字段文档、取值规则与 `size` 预占全部删除；同批里"技能正文 = 静态过程 + 现算动态表"的**动态表**也一并删除（技能回归纯静态）。本节**继续有效**的部分：三处载体的分工（公告 / 技能 / 工具 schema），以及第 3 条的档位顺序纪律（顺序只认条目 `values.resolution_order`，绝不按数组位置判断高低）。现状见下面的「额外参数退场（第十一批 / #659）」与「参数面收缩为五个（第十二批 / #661）」。
>
> **其中"档位顺序"一条再被取代（第十三批 / #663）**：第 3 条的"顺序只认条目 `values.resolution_order`、绝不按数组位置判断高低"自本批失效——v2 的枚举描述符 `values` 顺序**就是**从低到高，按位置判高低正是对的；上面那句"服务端按字典序排、数组没有顺序语义"只对 video / chat 条目（仍 `capabilities`）成立。现状见下面的「目录条目 v2」。

服务端契约侧的完整设计见 [`src/docs/design/2026-09-15-catalog-capability-semantics-design.md`](../../src/docs/design/2026-09-15-catalog-capability-semantics-design.md)（提案 #640）；本节只记**插件侧的为什么与纪律**。

**要解决的问题**：目录从此会下发 `capabilities.parameters`（这个模型收哪些 Canonical 字段）与 `semantics`（它属于哪一族参数语言）。在此之前，插件能发出去的字段是**编译进包**的六个，上游多一个参数就得改插件、重新构建、重新同步 profile。

**分工**：技能负责「理解」，透传负责「新参数」。

1. **技能用可选注入注册**：`ctx.inject(['skills'], sctx => sctx.skills.registerProvider(...))`，**不**放进 `src/index.ts` 的硬 `inject` 数组。理由与 `settings`、`directoryPicker` 同款：技能是增强面，生图、素材库、画布是主面；缺 skill 子系统的宿主上，整个插件不能因此不装配。`index.test.ts` 现在断言这四个服务**必须存在**（`tools`/`webServer`/`systemPrompt`/`attachments`）、且 `settings` 刻意**不在**硬 `inject` 里（它走可选注入）——**没有**长度断言，所以"加第五项会不会被测试拦住"指望不上这条断言，纪律靠这里记的这条规则。`@deepseek-ai/dsh-skill` 进 `devDependencies`（与既有 DSH 包一致，都是 devDeps）。
2. **技能正文 = 随包静态过程 + 现算动态表**（**第四批改写**；原为"纯静态资源"，原话"正文不含模型名与档位表"随之失效——现在只有**静态过程部分**不含，**动态表部分**包含且仅包含已保存模型）：静态部分（`assets/seework-image-capabilities.md`）讲怎么读目录、各族参数语言与常见坑，以及下面第 3-5 条的档位判断过程；动态部分在每次加载时按当前配置与已缓存目录现算。宿主为什么支持这样做见「公告瘦身与技能按需承载（第四批）」。
3. **档位高低只读语义端点的 `resolution_tiers`，绝不读目录数组的顺序**。目录里的能力数组**没有顺序语义**：服务端取并集后按**字典序**排序（`src/service/src/gateway_models/plan.rs` 第 154-166 行 `sort_by_key(|v| v.to_string())`），实证是 gemini 声明的 `["512","1K","2K","4K"]` 到目录里会变成 `["1K","2K","4K","512"]`，seedance 金样则是 `["1080p","480p","4k","720p"]`。若照数组顺序取"下一档/最高档"，gemini 上会把 `512` 当成最高清——正是这条技能最不能错的地方。做法：目录数组只当**集合**（这个模型有哪些档），顺序取语义端点的 `resolution_tiers`（该族的高低序，服务端声明），两者求交即得该模型的有序档位表。插件不自己按 K 值排大小，也不硬编码档位表。（**#669**：`src/tier-order.ts` 与其测试已删除——它只被自己的测试消费；「更高清」的判断由 Agent 按技能正文执行，插件不在请求层替它选档，档位顺序就是条目 `values` 的顺序。）**（第九批更正**：档位顺序的来源已从族端点改为条目 `values.resolution_order`，`orderTiers` 随之删除；本节其余口径不变，见上方第九批条目。）
4. **空档不降级、不猜**：目标档位 × 当前比例在 `gpt_image_product_profile.sizes` 里为空时，向用户说明该组合不存在并请其选择，而不是自动退到相邻档位（与仓库既有的「闭合拒绝、不降级」一致；`gpt-image-2` 现在 24 组全有值，但不能因此假设所有族都满）。
5. **「高清」的判断**：用户没提清晰度 → 用设置里的默认档位（默认 `1K`）；说「更高清/高清」→ 取比默认**高一档**（不是最大档）；说「最高清」→ 取最大可用档；已是最高档则保持并说明。
6. **部署现状得让 Agent 看得到**（**第四批改写**：公告尾部不再列任何逐型号的透传或值域细节——只给「默认模型的名字 + 一行能力（档位顺序 / 比例 / 参考图上限 / 一次最多几张）」与「其他**已保存**模型的名字清单」，再加一句"要更多细节就加载 SeeWork 技能"；**可透传字段**与 `size` 的口径**整体移入技能的动态表**，公告里不再出现）：**可透传字段** = `parameters` **减去插件自己的请求字段**（`mode` / `model` / `prompt` / `n` / `resolution` / `aspect_ratio` / `quality` / `output_format` / `image_urls`，外加 `image_urls` 的别名 `image` 与内部名 `refNames`）**再减去设置 owner 字段**（`watermark` / `seed`，第 7 条禁止 `params` 携带它们）。**（第八批更正：这第二项减法已删除——`watermark` / `seed` 本来就是目录声明的请求参数，现在与其它透传字段一视同仁地列进动态表。下面的"否则会出现说有、传了又丢"正是当年为了绕开这个错误判断才写的绕路。）**否则会出现"说有、传了又丢"的矛盾——`watermark` 必然出现在 seedream 的 `parameters` 里。`size` 与 `resolution` + `aspect_ratio` 互斥、而插件默认会补这两个，所以**只有两个默认都为空时 `size` 才可透传**——这条判定跟着请求构造器走，不是跟着目录走。档位顺序同样按第 3 条取语义端点，不能照抄目录数组。**这三条口径"给模型看的那一份"只有一个实现落点：`src/model-summary.ts`（第四批新增的共享 owner）；公告与技能都只渲染它算出的结果，各自不得重算。请求侧另有落地，不算第二份口径**：透传字段到底发不发由 `settings.ts::normalizeParams` 校验、`engine.ts::buildGenerationBody` 兜底（未知字段是 400）；张数上限则是**插件自己的**上限（线协议把上限留给模型的 `capabilities.max_images`，`docs/api/images.md` 不再写 1–10），由 `protocol.ts` 的 `MAX_IMAGES_PER_REQUEST` 一个常量供五处引用（设置默认值、出站请求体、工具 `n` 参数、设置卡片输入、展示层），不再各写一遍。**（#668 更正：上面这份「五处引用」已不准确——设置卡片的「每次张数」输入在 #658/D-15 就删了；`n` 的**合成**（模型上限 ∩ 插件上限，下限 1）自 #668 起收在 `protocol.ts` 的 `effectiveImageCount()` / `imageCountCeiling()`，归一化、出站体、工具 `n` 参数与公告四处都取它的结果，任务记录与素材库条目因此与真正发出去的数一致（此前 `settings.ts` 漏了插件上限：入库存 15、出站发 10）。同批把**比例默认**也统一到一处：`settings.ts::defaultAspectRatioFor()`（与 `defaultOutputFormatFor` 同形），面板与工具两条路同行为，模型不接受这个默认值就静默省略、不再以 `invalid_value` 回告模型。）**
7. **`params` 透传的范围与优先级**：
   - 只承载 `GenerateRequest` **之外**的字段；插件自己的请求字段（`mode` / `model` / `prompt` / `n` / `resolution` / `aspect_ratio` / `quality` / `output_format` / `image_urls`，含别名 `image` 与内部名 `refNames`）仍走具名参数，同名键出现在 `params` 里时以具名参数为准并回报 `conflict`（不做静默覆盖）。
   - `watermark` / `seed` 的唯一权威是插件设置（`src/engine.ts` 现有写入路径）；`params` **不得**携带它们，避免两个权威。**（第八批 #653 收尾：整条失效**——它们是 doubao 协议的请求参数，设置所有权已删；现在与其它声明过的字段同路透传，缺省即网关默认。见「水印与种子回归普通参数（第八批）」。）
   - 只透传目标模型 `parameters` 明示过的字段；未声明 → 丢弃并回报 `unsupported_field`。
   - 值规则（枚举 / 区间）**从目录读**：`capabilities` 里的字符串数组当枚举、`{min, max}` 当区间、`size` 从产品档案 `sizes` 的档位键与像素串派生（实现见 `src/catalog.ts` 的 `parameterRules`）。值不满足规则 → 丢弃并回报 `invalid_value`。`dropped` 要有**结构化原因**（`unsupported_field` / `invalid_value` / `conflict`，冲突时附一句可读 `hint`），把「字段未声明」与「值非法」分开，否则回报会失真。
   - 丢弃结果**必须回到模型看得见的地方**（工具结果的 message）：只把 `droppedParameters` 放进任务载荷，Agent 看不到「我传的参数没发出去」，回报就等于没有。
   - 目录没有下发 `parameters`（老快照、或来自裸 `/models` 的条目）→ **一律不透传**并回报：这里与「值未知就不裁剪」的既有宽松口径相反，因为发未知字段的后果是 `400 unknown_field`，安全优先。
   - 透传**不绕过**既有的 `capability.ts::resolveRequest` 裁剪与门控；明显冲突的组合（如 `size` 与 `resolution`+`aspect_ratio` 同传）由客户端先行拒绝并给可读提示。

## 任务语义与面向模型的表述（第十批 / #658）

> **部分已被取代（第十三批 / #663）**：本节里"`resolution` 缺省取该模型已发布有序档位的最低档（顺序未知则不填）"自本批失效——缺省改读服务端下发的 `resolution.default`（**只读它、不兜 `values[0]`**；缺失即契约违约，不填不猜并在公告的档位行如实上报），且因省略不等价而**必须显式发**；`SHARED_ARG_DESCRIPTION` 里那句"Omit to use the model's lowest tier"随之改成"目录为该模型声明的缺省档"。并发 / 不排队 / 不重试与其余参数缺省继续有效。现状见下面的「目录条目 v2」。

**现状**：**一次调用 = 一次生成请求**。同一模型同时只允许 1 个，插件**不排队、不自动重试**：忙时第二次提交直接拒绝（"本次未发起、未扣费、需许可再发"），不同模型互不影响。失败如实告知用户，得到许可后再发。面向模型的文本随之收敛：两个工具的 description **逐字相同**（只差第一句），共享参数**各一句话（作用 + 默认值）**——`n` 默认 `1`、`resolution` 缺省取该模型**已发布有序档位的最低档**（顺序未知则不填）、`aspect_ratio` 取**网关统一的 8 个比例**（默认 `3:4`）、`output_format` 出厂 `png`。设置里不再有「每次张数」「默认档位」，比例与输出格式改下拉；错误文案只陈述事实，不再出现"请勿重试，等它结束后再试"这类操作指令。（**#661 收缩**：共享参数由六个收缩为五个——`quality` 整条删除，上面那句"`quality` 缺省即 `auto`"随之失效；现状见下面的「参数面收缩为五个（第十二批 / #661）」。**第十四批 / #664**：面向模型的工具面合并为**一个** `generate_image`，本节"两个工具的 description **逐字相同**（只差第一句）"随之失效——`reference_images` 成为同一个工具的可选参数；现状见下面的「工具面合并为一个 generate_image（第十四批 / #664）」。）

**为什么**：此前把"实现约束"写成了"给模型的操作步骤"（"do not retry … wait for it to finish"），被读成"模型要自己排队"。现在**排队语义由插件承担**（干脆不排队、忙就拒），**模型只被告知事实**。逐条决策（D-1~D-17）、文案正式稿与两轴复核见 [`docs/design/2026-09-16-generation-task-semantics.md`](design/2026-09-16-generation-task-semantics.md)。

## 工具级约定归位到工具描述（第五批）

> **部分已被取代（第十批 / #658）**：本节里"工具描述承载**先确认提示词与比例**""同一模型串行时**别重试**""两个工具**各自**写全自己那份"三处已作废——确认契约后置到"技能方案"，串行/重试表述改为只讲事实（每模型 1 个、不排队、不重试），两个工具的描述改为共享常量 + 各自第一句。现状见上一节。
>
> **再被取代（第十四批 / #664）**：本节"每个工具描述**各自**写全自己那份"这个例外也随工具面合并作废——现在只有一个工具、一份描述，`reference_images` 是它的可选参数。现状见下面的「工具面合并为一个 generate_image（第十四批 / #664）」。

**现状**：`generate_image` / `edit_image` 的 `description` 现在承载**工具级调用与结果约定**——先确认提示词与比例、别自己编参数、默认值来自插件设置（含出厂默认）、结果字段 `file` / `url` / `path` / `absolute_url` 各是什么、**要在回复正文里用 Markdown 图展示**、同一模型串行时**别重试**、`edit_image` 的 `reference_images` 原样回传。这些句子已从**公告**里删掉（公告只留插件级事实：身份、两个工具、网关与目录地址、默认模型一行、其他已保存模型名字、素材库/画布在哪、怎么配置、"生图 / 改图前先加载技能"的指令（**#665** 改，原文这里写"技能指针"），以及**每模型一次的并发上限**这类限制本身）；技能正文只留过程（**第十一批 / #659：动态表已删除**，技能是纯静态文件，且"先确认提示词与比例"的口径另见第十批注记）。**两个工具描述是常量**（模块级字符串，不随配置变）；**公告不是**——它由 `guidanceFor` 按当前设置现拼，只有那段"默认模型一行 + 其他模型名字"随目录变。

**为什么**：工具描述随工具定义每轮常驻，**不受 `announceToAgent` 管辖**——只有放这里，用户关掉公告（`announceToAgent=false`）后模型才仍然知道该怎么调、怎么展示结果。反过来说，插件级事实放进工具描述会挤占"模型选哪个工具"的注意力，随配置变的内容放进描述会逼着每次提交重注册工具，所以两边都不越界。两个工具**各自**写全自己那份（选择某个工具的模型可能只读那一条），但同一句话**措辞相同、且只有两处**，不出现第三种说法。

## 目录自动检测（第六批）

**现状**：目录不再只由用户点「检测可用模型」刷新。`src/catalog-refresh.ts` 的一个 refresher 实例接三个触发点——**宿主启动各跑一次**、**打开设置卡片**（`POST /api/dsh-seework/catalog/refresh`，受节流）、**低频后台**（`DEFAULT_REFRESH_INTERVAL_MS`，6 小时常量，宿主结束即停）。一轮里：**已保存模型的能力自动采纳**（含 `discoveredAt` 重新盖时间戳），**新模型只报告**（卡片把新行预勾选，用户一次「保存模型」即可加入），**消失的模型只报告**（快照保留）。没配 Key 或没有已保存模型时**一个请求都不发**；失败与"没变化"都静默，且**没采纳就不写设置文档**——一轮只写 `models` 这一个字段，用户的选择与默认模型不受影响。公告仍是"默认模型一行 + 其他模型名字"，所以刷新后 Agent 下次加载即见新数据。（**第十一批 / #659**：技能侧的"动态表每次加载现算"已不存在；逐模型的字段事实改由该模型的 `/guide` 承载。**第十二批 / #661**：`/guide` 指引也删除——插件不再指路。另有一个例外进了"没采纳就不写"：文档里还留着退场键时，那一轮即使没有采纳也会写回 `models` 把残留清掉——只写这一个字段，且不报"已刷新"。<br>**#661 追加的退场键**：`RETIRED_MODEL_KEYS` 多了 `qualities`，所以一个只带着该键的老文档同样会触发这一轮清理写。）
